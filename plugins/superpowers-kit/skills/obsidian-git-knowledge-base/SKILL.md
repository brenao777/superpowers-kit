# Obsidian Git Knowledge Base

Работай с vault как с обычной папкой Markdown-файлов. Obsidian — интерфейс к этим файлам, поэтому отдельный MCP для базовой работы не нужен.

## Границы и защита данных

- До изменений определи корень vault, наличие Git, удалённого репозитория, существующие правила и статус рабочей папки.
- Не настраивай Git поверх iCloud Drive, Dropbox, Google Drive и других папок с активной файловой синхронизацией. Объясни риск конфликтов и попроси выбрать обычную локальную папку.
- Перед каждым изменяющим действием сообщай одной строкой, что именно будет сделано. Не удаляй файлы и не перезаписывай существующие правила без явного согласования.
- Не переименовывай и не перемещай Markdown-файлы: это может сломать ссылки `[[...]]`, которые Obsidian исправляет только при перемещении внутри самого приложения.
- Не помещай в vault пароли, API-ключи, сессии или финансовые документы.

## Выбери режим

### Полное подключение с нуля

Используй, когда пользователь просит создать vault и провести его через всю настройку. Прочитай [onboarding](references/onboarding.md) и выполни маршрут целиком. Пользователь уже авторизовал эту последовательность: сообщай одной строкой перед каждым изменением, но не останавливайся между обычными локальными шагами. Остановись только там, где пользователь должен сам пройти браузерную авторизацию GitHub, подтвердить системную установку или открыть vault в графическом интерфейсе Obsidian.

### Новый vault и GitHub

Используй, когда пользователь хочет создать хранилище, подключить GitHub или настроить синхронизацию. Прочитай [порядок настройки](references/setup.md).

Если vault ещё не существует, сначала попроси путь к новой локальной папке и создай её вместе с `Входящие/`, `Заметки/` и `Гайды/`. Не создавай vault внутри iCloud Drive, Dropbox или Google Drive. Затем попроси пользователя открыть созданную папку в Obsidian через **Open folder as vault**; взаимодействовать с графическим интерфейсом Obsidian для этого не требуется.

Сначала создай `.gitignore`, затем сделай первый коммит. Если нужно создать репозиторий на GitHub, он должен быть приватным. Не обещай, что Git даёт мгновенную синхронизацию: Obsidian Git работает по интервалу и забирает изменения при запуске.

### Правила для Codex и Claude Code

Используй, когда пользователь хочет дать агентам единые правила. Прочитай [политику vault](references/vault-policy.md). Создай одинаковые `AGENTS.md` и `CLAUDE.md` в корне только если их ещё нет; при наличии сначала покажи различия и предложи безопасное объединение.

### Работа с базой

Можно читать, искать и анализировать любые заметки. Новое сырьё можно создавать только во `Входящие/`. Для `Заметки/` и `Гайды/` сначала предложи содержимое или явный список файлов; меняй их лишь после подтверждения пользователя. Каждая новая заметка начинается с заголовка, а внизу содержит раздел `Связано` со ссылками на существующие заметки.

При разборе `Входящие/` сначала выдай группировку и черновики, не создавай обработанные заметки сразу. Указывай исходные файлы, не додумывай факты и оставляй пользователя редактором.

### Конфликт или обслуживание

Не разрешай Git-конфликты автоматически. Покажи затронутые фрагменты, сохрани обе версии смысла и попроси выбрать итоговую формулировку. Для еженедельной уборки сначала составь отчёт: дубли, заметки без связей, устаревшие фрагменты и предложения; изменения вноси только после подтверждения.

## Когда нужен MCP

Не предлагай Obsidian Local REST API/MCP для чтения и обычных файловых операций. Рассматривай его только когда пользователь явно просит точечные команды в открытом Obsidian и понимает, что приложение должно быть запущено на том же компьютере.
