# Базовая защита VPS

Настрой защиту выделенного VPS и сохрани административный доступ. Работай из Codex или Claude Code через доступный SSH-клиент. Установка агента на сервер и подключение Telegram не требуются.

## Границы и доступ

- Поддерживаются Ubuntu и Debian с systemd и OpenSSH Server. Для другой системы остановись до изменений.
- Используй переданные адрес, SSH-пользователя, порт и способ входа. Если их нельзя определить из текущей задачи или SSH-конфигурации, запроси только недостающие данные. Не подключайся к случайно найденному серверу.
- Пароль вводи через приглашение SSH или приватный механизм инструмента. Не записывай его в команды, Git и отчёт. Не выводи приватные ключи и файлы авторизации.
- Сверь адрес с запросом и используй known_hosts. При первом входе сверяй fingerprint с панелью провайдера, если он доступен; без независимой сверки обозначь trust-on-first-use. При смене известного ключа остановись, не удаляй запись для обхода ошибки.
- Не меняй SSH-порт, пользователей, sudo-права, облачный firewall и приложения. Не выполняй полный upgrade и перезагрузку сервера без отдельного запроса.
- Запрос на базовый харденинг разрешает описанные ниже изменения. Кратко объясни их перед выполнением. При просьбе только проверить сервер ограничься чтением.

## 1. Осмотр до изменений

Определи ОС, виртуализацию, наличие systemd, административные права, текущего SSH-пользователя и адрес клиента. Проверь слушающие TCP/UDP-порты и сервисы, фактические SSH-порты, состояние UFW и Fail2ban. Используй `/etc/os-release`, `systemd-detect-virt`, `id`, `ss -lntup`, `sshd -T` и команды статуса с нужными правами.

При socket activation порт может задаваться `ssh.socket`. Сопоставь `sshd -T` с `ss`, `SSH_CONNECTION`, unit-файлами SSH и пробросом портов провайдера, если он есть. Различай внешний порт подключения и порт на интерфейсе VPS.

Осмотри Include/Match в OpenSSH, `/etc/ssh/sshd_config.d/`, cloud-init, правила UFW/nftables/iptables и признаки управления конфигурацией. Cloud-init сам по себе не запрещает настройку: выясни, какие файлы он генерирует, и не редактируй их вслепую.

На занятом сервере с Docker, Kubernetes, VPN, сторонним firewall или неизвестными публичными сервисами остановись до сетевых изменений и согласуй конкретные правила сохранения доступа. Не включай `deny incoming`, предполагая, что нужен только SSH.

Покажи обнаруженные ОС, доступ, SSH-порты, сервисы и план. Если не можешь сохранить открытую рабочую SSH-сессию для отката, сначала обеспечь проверенный способ восстановления, например консоль провайдера или отложенный откат; без него не меняй firewall и SSH-аутентификацию.

## 2. Ключ оператора и независимая проверка

Используй подходящий существующий ключ. Если ключа нет, создай локально пару ed25519 с уникальным именем в пользовательском SSH-каталоге. Не перезаписывай ключи и не копируй приватную часть на сервер. Сообщи путь к ключу и необходимость резервной копии.

Добавь публичную часть в `authorized_keys` административного пользователя, без дубликатов и с сохранением остальных строк. Проверь владельца, права `.ssh` (`700`) и `authorized_keys` (`600`); не ослабляй ограничения ключей. Если ключи управляются внешним хранилищем, сохрани этот механизм.

Из отдельного соединения проверь ключ, отключив пароль, keyboard-interactive и повторное использование открытого SSH-соединения:

```bash
ssh -p <EXTERNAL_SSH_PORT> -i <PRIVATE_KEY> \
  -o IdentitiesOnly=yes -o BatchMode=yes \
  -o PreferredAuthentications=publickey \
  -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no \
  -o ControlMaster=no -o ControlPath=none \
  -o UserKnownHostsFile=<KNOWN_HOSTS> -o StrictHostKeyChecking=yes \
  <SSH_USER>@<VPS_HOST> 'echo KEY_OK; id'
```

Подставь проверенные значения с экранированием для текущей оболочки. Проверь код завершения, `KEY_OK`, пользователя и возможность выполнять административные команды. Для зашифрованного ключа используй локальный ssh-agent, не снимай пароль с ключа. Для встроенного SSH-клиента выполни эквивалентную проверку новой аутентификации по ключу.

При неудаче остановись: не включай UFW и не отключай пароль. Наличие `authorized_keys`, запись в журнале и открытая сессия не заменяют эту проверку. Попроси пользователя проверить второе подключение вручную только если агент сам не может его открыть.

## 3. Резервные копии и порядок изменений

До записи сохрани изменяемые файлы, права, владельцев, состояние сервисов и правила/политики UFW в приватный каталог root с уникальной UTC-меткой. Запиши, какие файлы созданы этим запуском и каких не было раньше. Храни копии вне каталогов `*.d`, чтобы они не загружались как настройки.

Используй отдельные файлы с комментарием `Managed by vps-basic-hardening`. Чужой файл с тем же именем не перезаписывай. При повторном запуске меняй только отличающиеся настройки, не дублируй правила и не перезапускай исправные сервисы без необходимости.

Сохраняй исходную SSH-сессию до конца проверок. Проверяй каждый этап перед следующим. При ошибке откати проблемный этап и остановись.

## 4. UFW

1. Установи `ufw` из репозитория ОС, если его нет. Не выполняй `ufw reset`.
2. До включения firewall разреши каждый фактически используемый порт SSH на интерфейсе VPS по TCP. Учти IPv4 и IPv6, если они используются; не отключай IPv6 ради упрощения. Не предполагай порт 22 и не полагайся на профиль `OpenSSH` при нестандартном порте.
3. Сохрани существующие разрешения и более строгую исходящую политику. Для нового VPS без специальных сетевых требований задай `deny incoming` и `allow outgoing`, затем включи UFW.
4. Проверь `ufw status verbose` и новое независимое SSH-соединение способом из этапа 2. При отказе восстанови исходные правила, политики и состояние UFW из открытой сессии. Не обнуляй общие таблицы nftables/iptables.

Не открывай HTTP, HTTPS, панели, Telegram и другие порты без потребности из запроса. Telegram polling использует исходящие соединения.

## 5. Fail2ban

Установи `fail2ban` из репозитория ОС, если его нет. Создай управляемый `/etc/fail2ban/jail.d/90-vps-basic-hardening.local`, сохранив другие jail и не меняя `jail.conf`:

```ini
[sshd]
enabled = true
backend = systemd
port = <SERVER_SSH_PORTS_COMMA_SEPARATED>
maxretry = 5
findtime = 10m
bantime = 1h
```

Подставь реальные порты на VPS, например `2222` или `22,2222`. Для backend systemd не добавляй `logpath`; проверь доступность Python systemd bindings и чтение SSH-журнала. При отсутствии зависимости установи соответствующий пакет ОС.

Проверь порядок остальных `.local` файлов и итог через `fail2ban-client -t` и при необходимости `fail2ban-client -d`. Сохрани более строгие действующие ограничения, если они совместимы с запросом. Не подменяй чужой banaction без выяснения его совместимости с firewall.

После успешной проверки включи автозапуск и запусти сервис; для работающего сервиса используй штатный reload. Проверь `systemctl is-active fail2ban`, `systemctl is-enabled fail2ban`, `fail2ban-client status sshd`, фактические параметры jail и новое SSH-подключение. Не имитируй перебор с адреса оператора. При ошибке восстанови свой файл и прежнее состояние сервиса, сохранив другие jail.

## 6. SSH только по ключу

Повтори проверку ключа перед отключением пароля. Осмотри `AuthenticationMethods`: если он требует пароль или keyboard-interactive вместе с ключом, остановись для согласования вместо удаления второго фактора.

Создай ранний управляемый drop-in, например `/etc/ssh/sshd_config.d/00-vps-basic-hardening.conf`:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

Сохрани текущую политику root. Если `PermitRootLogin yes`, добавь `PermitRootLogin prohibit-password`, сохранив root-вход по ключу. Не ослабляй `no`, `prohibit-password` или `forced-commands-only` и не отключай root-вход без отдельного запроса. Не меняй `UsePAM` и sudo-пароль.

Имя файла не гарантирует приоритет: у большинства директив OpenSSH применяется первое найденное значение. Проверь положение Include, Match и поддержку drop-in. Если нужно изменить основной файл, сделай минимальную правку с backup, сохранив чужие настройки; не применяй массовый `sed`.

До применения выполни `sshd -t`, затем `sshd -T` и `sshd -T -C user=<USER>,addr=<CLIENT_IP>,host=<CLIENT_HOST>,laddr=<SERVER_IP>,lport=<SERVER_PORT>` с реальными параметрами подключения. При Match Host используй имя клиента, которое видит сервер. Проверь контексты административных пользователей и все Match, способные снова разрешить пароль. Не объявляй пароль отключённым для всего сервера, проверив только один контекст.

Ожидаются `pubkeyauthentication yes`, `passwordauthentication no`, `kbdinteractiveauthentication no` и сохранённая политика root. Если синтаксис или значения неверны, восстанови свои файлы и не применяй конфигурацию.

Сделай reload фактического сервиса `ssh` или `sshd`, определённого при осмотре, без restart и изменения socket activation. Проверь статус и новое независимое подключение по ключу. При отказе немедленно восстанови только свои SSH-изменения из исходной сессии, выполни `sshd -t` и reload; проверь восстановление доступа и остановись.

## Приёмка и отчёт

Проверь UFW, разрешённые SSH-порты, Fail2ban и jail `sshd`, автозапуск сервисов, эффективные SSH-настройки и новый вход по ключу. Если до настройки работало приложение, проверь сохранение его доступности. Исходная сессия не доказывает возможность нового входа.

Сообщи, что включено, какие порты разрешены, параметры блокировки Fail2ban, статус парольного входа, результат нового подключения, пути к ключу, управляемым файлам и backup. Перечисли пропущенные и непроверенные этапы. Успех возможен только после фактических проверок; не обещай полной защиты от всех атак.
